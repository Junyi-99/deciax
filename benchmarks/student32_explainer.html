00 / 轴词典

全文 shape 写作 [128seq, 384hidden]：数字是长度，后面的词是这条轴的含义。batch 恒为 1，全部省略。

轴长度含义
seq128序列位置轴，长度是 pad 后的 token 个数。每个位置上是一个 token 的 384 维向量；mask 标出哪些位置是真实 token。和 lane 的 128 无关。
query / key128 / 128attention 里 seq 轴的两个角色：query 是正在计算输出的位置，key 是被查看的位置。本 kernel 的 score 矩阵是 [key, query]，softmax 沿 key。
hidden384模型隐藏宽度。LayerNorm 沿这条轴求均值和方差。
head / dim6 / 646 个 attention head，每个 64 维；head×dim = 384。在 qkv 和 att 中 6 个 head 沿 lane 并排：head h 占 lane h·64 … h·64+63。
qkv1152Q、K、V 三段各 384 并排：lane 0–383 是 Q，384–767 是 K，768–1151 是 V；每段内部再按 head×dim 排。
ffn640 / 1536FFN 中间宽度。encoder 为 gated GELU，每支逻辑宽 576，补零到 640，两支并排为 1280。decision 层为 ReLU，宽 1536。
vocab50368词表行数。embedding 表每行一个 token 的 384 维向量。
lane128TPU 向量寄存器的列宽，和 seq 的 128 只是数值相同。逻辑上不足 128 的最后一维补到 128：scorer 的 1 列、feature 的 4 列、action 的 2 列。
sublane8TPU 向量寄存器的行数。按 8 行对齐读写：embedding 取块、marker 取块、输出打包。
repetition9kernel 内第几次 forward。第 0 次是 warmup，1–8 是 8 组不同输入。
type / option3 / 2question type 数；本次每个问题的选项数。

01 / 一次前向

模型 ckpt-32m-fp，encoder 为 models/ettin-encoder-32m。整个模型是一个 Pallas kernel，所有权重在 kernel 开始时从 HBM 搬进 VMEM，9 次 forward 复用。tokenization 和最终校准解码在 CPU 侧，不在 kernel 内。

Embedding按 ID 取行，再 LayerNorm
→
Encoder × 10RoPE · 每 3 层 1 层全局 attention · gated GELU
→
Final LN + type按 question type 选 3 行之一
→
Decision × 2全局 attention · ReLU FFN · 带 bias

选项分支（scorer）

先给全部 128 个 token 打分，再按 marker 位置取 2 个。

Action 分支

4 个特征：top1 概率、top1−top2、熵（bit）、选项数/255。

输入

名称shape内容
metaSMEM · scalar prefetch每次 forward 131 个 int32：128 个 token ID，2 个 marker 位置，1 个 question type。
mask1 = 真实 token，0 = padding。
权重kernel 输入，整块 DMA 进 VMEM。PyTorch 的 [out, in] 已在准备阶段转置；下文矩阵 shape 都是 kernel 里的 [in, out]。

VMEM scratch

名称shape · dtype用途
xbuf残差流。每层结束写回。
qkv三次投影的结果（Q、K 已加 RoPE）。
att6 个 head 的 PV 输出，按 head 写入行 h·64 … h·64+63。注意是转置布局。
scorescorer 输出，只有 lane 0 有效。
outkernel 输出。每次 forward 一个 [8,128] 块。

Embedding lookup（scope embedding_lookup / embedding_token_group）

每次查表只查一个 token。查询的 key 是这个 token 的 ID（SMEM 里的一个标量），用它对 embedding 表做一次动态切片，读出 8 行对齐块。128 个 token 就是 128 次独立的单 token 查询。embed_group=8 只是把 8 次查询的结果拼成一块后一次写回 xbuf，不是把 8 个 ID 一起 gather。

为什么 score 是 [key, query]，att 是 [head×dim, query]？

每个 head 算 K × Qᵀ 得 ，softmax 沿 key（axis 0）。接着 Vᵀ × P 得 ，直接写进 att 的 64 行。输出投影把 att 和 Wo 同时沿 axis 0（head×dim）收缩，结果回到 。这样 6 个 head 的结果不需要再转置就能拼起来（pv_transposed=true）。

head_group=6：6 个 head 的 QK 和 softmax 先全部发出，再依次做 6 个 PV，让 MXU 和 EUP 的工作交错。

06 / 打开真实 trace

点击按钮打开 Perfetto 并通过 postMessage 载入本页内嵌的 trace。首次打开需要联网加载 Perfetto。

  1. XLA TraceMe 轨道里找 embedding_norm，到对应 output_pack 结束是一次 forward 的主体。每个 kernel 的第一次 forward 是 warmup。
  2. 搜索 encoder_00、decision_00、head_0_softmax 等 scope 名。
  3. 展开 MXU0/1、VALU、EUP、XLU、VLD/VST Instructions 各 lane，对照 Framework Name Scope / Source code 看每个 scope 落在哪些指令上。选中时间片按 F 聚焦。lane 是显示行：同一时刻互相交错的事件各占一行，嵌套的 scope 在同一行内层叠。指令轨道里的层叠只表示时间区间包含，不是调用关系。
